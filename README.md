### Проделанная работа

#### Спринт 1: Архитектура бэкенда (Рефакторинг)

Исходный код бэкенда представлял собой монолит, где в одном файле (`service.py`) смешивались HTTP-запросы, бизнес-логика, файловые операции
и SQL-запросы. Это нарушало принцип единственной ответственности (SRP) и делало код нетестируемым.

**Что было сделано:**

- **Внедрена слоистая архитектура (Layered Architecture):** Проект разбит на независимые слои: `api` (роутеры), `services` (бизнес-логика) и
  `repositories` (слой доступа к данным).
- **Паттерн Репозиторий:** Вся работа с SQLAlchemy (SQL-запросы, сессии) изолирована в `repositories/`. Сервисы больше ничего не знают о
  таблицах базы данных напрямую.
- **Dependency Injection (DI):** Связывание слоев реализовано через систему зависимостей FastAPI (`Depends`). Это позволяет легко подменять
  реальные репозитории на моки (mocks) при написании Unit-тестов.
- **Централизация конфигурации:** Захардкоженные `DB_URL` и пути к файловой системе вынесены в `core/config.py`, образуя единую точку
  управления настройками.
- Исправлена ошибка сборки Docker-образа фронтенда (удален ошибочный шаг копирования несуществующего файла `.env.production`).

#### Спринт 2: Оптимизация производительности (Бэкенд)

Исходный код содержал критические уязвимости, приводящие к переполнению оперативной памяти (OOM) и блокировкам Event Loop'а при работе с
большими файлами.

**Что было сделано:**

- **Потоковая загрузка файлов:** Использование `await upload_file.read()` заменено на асинхронную передачу файла чанками напрямую на диск
  через `shutil` и пул потоков (`run_in_threadpool`). Это позволяет безопасно загружать файлы любых размеров.
- **Оптимизация Celery-воркеров:** Анализ метаданных файлов (текст, PDF) переписан на потоковое чтение.
- **Устранение утечки ресурсов asyncio:** Самописная обертка для запуска асинхронных задач в Celery заменена на нативный `asyncio.run()`, а
  конфликт пулов SQLAlchemy решен внедрением `NullPool`.
- **Оптимизация ORM (Проблема N+1):** В модели добавлены `relationship`, а запросы переписаны с использованием `selectinload` для
  предварительной загрузки связанных алертов.

#### Спринт 3: Декомпозиция фронтенда

Исходный `page.tsx` представлял собой монолитный компонент, нарушающий DRY и смешивающий слои абстракции (сетевые запросы, локальный стейт,
бизнес-логику и JSX-верстку).

**Что было сделано:**

- **`types/`**: Выделены интерфейсы `FileItem` и `AlertItem` для глобального использования без циклических зависимостей.
- **`utils/`**: Функции форматирования (даты, размеры, бейджи) вынесены в чистые функции, готовые к unit-тестированию.
- **`api/`**: Сетевые запросы абстрагированы в `client.ts` — компонент больше не знает про `fetch` и URL-адреса бэкенда.
- **`hooks/`**: Вся логика управления состоянием и оркестрации запросов вынесена в кастомный хук `useFiles.ts`.
- **`components/`**: Раздутая верстка разделена на презентационные компоненты (`FilesTable`, `AlertsTable`, `UploadModal`), что сделало
  `page.tsx` читаемым и легко масштабируемым.

### Быстрый запуск (Quick Start)

Для развертывания проекта локально потребуется установленный Docker и Docker Compose.

1. **Соберите и запустите контейнеры:** Флаг `--build` гарантирует, что соберутся актуальные образы с нашими архитектурными изменениями.

    ```bash
    docker compose -f docker-compose.dev.yml up --build
    ```

2. **Примените миграции базы данных:** Выполните эту команду в новой вкладке терминала (не останавливая работу контейнеров). Без этого шага
   база данных будет пустой, и API вернет ошибку.

    ```bash
    docker exec -it backend alembic upgrade head
    ```

3. **Откройте приложение в браузере:**
    - **Клиентская часть (React):** [http://localhost:3000/test](http://localhost:3000/test)
    - **Документация API (Swagger):** [http://localhost:8000/docs](http://localhost:8000/docs)
